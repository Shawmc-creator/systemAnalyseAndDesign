# 费用审批与退款后端验收

日期：2026-10-18。依据定稿需求文档UC-24、UC-25、UC-26及费用申请、退款状态机实现。沿用85表SQLite基线；需求PDF、LaTeX和建表SQL未改，旧库未迁移。Figma与页面改版继续按用户要求暂停。

## 已实现

| 需求 | 岗位 | 本批代码 |
|---|---|---|
| UC-24申请费用调整与退费 | 收费人员 | 提交、退回后重提、待审核时撤回；同患者原账目/原款、金额、未完成申请及原单版本检查；重提完整保留前后值 |
| UC-25审核费用调整与退费 | 负责人 | 退回、拒绝、批准；原提交指纹及源版本核对；逐项调整、原用途释放、批准、资金与账目版本、审计共同提交 |
| UC-26办理与登记退款 | 收费人员 | 建立唯一办理号并占用额度；未知继续占用；核实成功或失败；失败后以新编号关联最近失败；部分退款及渠道交易查重 |

新增`src/v2/fees.js`、`fee-gates.js`。工作单元增加费用调整集合冻结、批准与调整明细等额、单项/账目/原款余额不负检查，保留既有幂等请求和当前授权检查。

## 接口

POST沿用登录Cookie、明确的`X-Clinic-Role`、`X-CSRF-Token`及`commandVersion:1,requestKey`；金额为整数分。源版本从查询结果读取，每阶段重新核对。

| 方法、路径 | 权限 | 输入 |
|---|---|---|
| POST `/api/v2/fee-requests/apply` | `uc24.apply` 收费人员 | `submit/resubmit/withdraw`；`patientId,billId,paymentId,expectedFundsRevision,expectedBillRevision,expectedPaymentRevision`；`adjustmentCents,refundCents,reason,evidence`；已有申请另填`requestId,expectedRevision` |
| POST `/api/v2/fee-request-decisions/approve` | `uc25.approve` 负责人 | `approve/return/reject`；`patientId,requestId,expectedRevision,reviewNote`；批准另需源版本、`adjustmentCents,refundCents,items,releases` |
| POST `/api/v2/patient-refunds/refund` | `uc26.refund` 收费人员 | `initiate`引用批准、原款及源版本、`amountCents,channel,recipientVerification`；失败重办另填`previousAttemptId` |
| POST 同上 | 同上 | `markUnknown/verify`；`patientId,refundId,expectedRevision,expectedFundsRevision,transactionEvidence,verificationNote`；核实填`outcome:success/failed/unknown,actualCents,recipientMatches,externalReference` |
| GET `/api/v2/fee-requests/query` | 收费人员 `uc24.apply`／负责人 `uc25.approve` | `patientId`；可选`status,page,pageSize`。返回申请、当前源版本、变更历史、调整明细、退款办理及授权剩余额，不返回病历正文 |

原账目和原付款至少选一项，重提不得更换原来源。申请调整为带符号金额，退款为非负金额。可选`clinicalCorrectionIds`仅接受与原账目执行链对应的实际更正ID；不以自由文本替代临床执行修改。

批准明细`items`每项为`billItemId,expectedRevision,amountCents,note`，须属于原账目且已核价，合计等于批准额，累计单项应收不得为负。`releases`每项为`kind:allocation/offset,id,expectedRevision,amountCents,reason`，金额填正数，服务追加负向释放事实，保留原用途ID、原款及申请。释放不超过本次应收减少及原用途剩余部分。

退款建立阶段须填`requestId,expectedApprovalRevision,paymentId,expectedPaymentRevision,expectedFundsRevision`；申请含账目时还需当前`expectedBillRevision`。`initiate`只建立记录，不调用银行。工作人员在线下实际办理后，回填原办理号的结果。

## 处理规则

- 申请本身不改变应收、已付或可用资金。相同原账目/原款存在待审核或退回事项时拒绝另开重复申请，提示已有申请号。
- 原单版本及申请内容指纹在提交审计中固定；审核时重新读取并核对。原资金/账目已变化时须退回重提，不能用刷新后的余额掩盖旧依据。
- 已支付1000元、正确应收800元时，批准减少200元与释放原用途200元共同生效，形成来源清楚的200元可用额。原账目明细、原收款和原正向用途均保留。
- 明细中的正负调整按最终合计核对，服务先保存正向明细，避免SQLite逐行检查误拒绝最终合法的混合调整。任一步失败，批准、明细、用途和版本全部回滚。
- 批准不是实际退款，也不会把授权额加入实际退款或占用。退款开始时再按批准剩余额、原款可用额双重限额建立占用；其他用途先使用余额后，原授权仍须重新核对。
- 同一原款有待办理或待核实退款时，不另起第二次退款，必须核实原办理号。未知不会释放额度；明确失败才释放，重办引用最近失败且不能分叉。
- 成功只计实际退款额，部分成功释放未实际执行的占用部分，剩余批准额度仍须重新校验后另办。原款可用额同时扣除分配、抵扣、成功退款和在途占用。
- 报告金额超出占用、接收信息不符、非现金缺少交易号，或报告失败却有正实付时，保存为待核实，返回`REFUND_REVIEW_REQUIRED`，保留原占用和观察证据供负责人核实。
- 非现金退款交易号在写锁内查重；同一办理号一旦关联交易号不得改指另一交易。终结的成功或失败原记录冻结。
- 同一提交号重试返回当时阶段回执，不重复审批、释放或登记退款；阶段回执不随后续状态被改写。当前办理进度通过查询读取。

完整命令：`../runtime/node.exe --test tests/*.test.js`。**145项通过，0项失败**；新增24项，新版累计88项，旧版回归57项。真实HTTP覆盖角色与CSRF拒绝、并发重复审批及退款、未知占用、确认原办理、费用查询和原阶段回执恢复。

其他检查包括原单过期、退回重提的旧意见、批准范围和明细合计、原用途释放、正负混合调整、临床更正引用、预付退款、部分实际退款、失败重办、交易重复、集合冻结、审批及退款审计故障后的完整回滚。

运行`npm run demo:fees:v2`，或`../runtime/node.exe scripts/demo-v2-fees.js`，会在独立内存库复现：

1. 原收款与应收均为1000元。
2. 提交减少200元的申请，原金额不变。
3. 负责人批准，应收及原付款用途共同变为800元，尚未退款。
4. 建立200元退款办理；结果未知时持续占用200元。
5. 核实原办理成功，实际退款200元；重复确认不会再次登记流出。

模拟日期固定为2026-10-19，数据为虚构软件演示，不接触运行库或支付平台。完整日志、JSON摘要和演示结果位于`../04-测试与验收/测试结果/20261018-v2-fees-refunds/`。

## 当前边界及下一步

- 本批提供后端及接口，新增网页仍待后续接入；没有把接口验收当作网页验收。
- 按当前C状态机，已同意申请是终态，本批不另加“撤销已批准授权”入口；已退回申请也不能跳过重提直接转撤回。
- 金额/接收信息差异以待核实记录、审计及负责人查询保留；专门的差异派单、跨岗位签收页面尚未接入。
- 退款核实依靠工作人员确认线下证据，不直接执行银行退款或自动判断凭证真伪。运行门禁尚未作长期数据量性能验收。
- 下一批优先复诊要求、联系、复诊关联及临床评估；随后继续材料、采购、器械和运行管理。32用例整体及旧数据迁移仍未全部完成。
