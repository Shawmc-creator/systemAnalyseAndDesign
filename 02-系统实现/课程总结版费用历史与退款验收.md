## 已完成

| 业务 | 实现与验证 |
| --- | --- |
| 价目提交、退回、重提、确认、停止新计费 | `service_price_history`保存当次单价、期间、制定依据、状态、审核意见及人员时间；改价不覆盖旧快照，重提清除当前审核结论，确认人和当前办理人分别记录 |
| 费用申请与审核 | `fee_request_history`逐次保留原账、原款、拟调整/拟退、证据、提交批次及审核决定；提交、退回、拒绝、同意、撤回各自追加，原行只表示当前结果 |
| 共同保存 | 主业务结果、历史、必要费用调整/原用途释放、请求结果及审计处于同一本地事务；历史或审计写入失败整体回滚，失败不占历史序号 |
| 历史不重复、不改删 | 恒定办理标识按账号及原提交生成；同请求重试返回原结果；原对象内序号递增，快照字段与当时原业务一致，表只追加且有明确外键 |
| 撤回责任 | 只有本次提交的收费人员可以撤回；他人重提后按真实新提交人判断。旧库先查可核对的原审计，不把未知后续提交人当作最初建单人 |
| 原渠道退款 | 选择原付款后，前端仅提供原渠道；后端拒绝改走另一渠道。建立办理占额、未知继续占额、确认实际金额和部分成功后的剩余额分别处理 |
| 岗位查询 | 收费与负责人可展开完整申请快照和价目历史；前台无费用申请查询权限，牙医目录不返回这些财务历史 |

新历史由独立的`FinancialHistoryRepository`负责字段装配和存取，业务方法决定何时追加。事务末检查业务当前结果是否有相应新快照，不能只更新主行而漏写历史。两张表字段、类型、主键及外键与现行模型逐项对应，没有另造业务类或用例。

## 验收与示例

**320项自动化检查通过，0失败。** 本批新增13项业务、2项迁移、1项HTTP检查，包含旧记录保留、第二张表创建失败回滚、历史禁止改删、伪造快照拒绝、权限/CSRF、旧提交责任、退款原渠道、未知占额及部分成功。

**12个隔离Chrome网页场景通过**，保存4张截图，脚本错误0，390像素窄屏无页面横向溢出。具体示例：

- 原实收1000元，首次申请减退200元；负责人退回后重提150元。四次快照分别保存首次申请、退回意见、第二次申请和最终批准，旧证据仍可查看。
- 批准并释放原用途后，不立即记实际退款；先建立150元办理。未知保持150元占额，核实仅实际退回100元后，已退100元与尚可办50元分列。
- 新价目100元被退回，修订为120元后重新提交、确认及停止新计费。五次历史保留当时价格与期间，原100元内容不被120元覆盖。
