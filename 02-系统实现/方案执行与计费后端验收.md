## 接口及输入

所有POST均需登录Cookie、明确的`X-Clinic-Role`、`X-CSRF-Token`及请求体中的`commandVersion:1`、唯一`requestKey`。角色按当前有效资格检查。

| 方法及路径 | 岗位／权限 | 主要输入 |
|---|---|---|
| POST `/api/v2/treatment-plans/plan` | 牙医 `uc22.plan` | `visitId,patientId,action`；`draft`填`goal,diagnosticBasis,plannedSchedule,reason,items`；已有版本填`versionId,expectedRevision` |
| POST `/api/v2/executions/execute` | 牙医 `uc04.execute` | `visitId,patientId,expectedVisitRevision,serviceId,planItemId,quantity,toothCode,surfaceCode,completedAt,procedureNote`；更正填`originalExecutionId,reason` |
| POST `/api/v2/service-prices/draft` | 收费人员 `uc05.draft` | `service`建立`name,billingUnit,reason`；`draft`填`serviceId,unitPriceCents,validFrom,validUntil,reason`；`submit`填`priceId,expectedRevision` |
| POST `/api/v2/service-prices/approve` | 负责人 `uc05.approve` | `approve/return/stop`填`priceId,expectedRevision,reviewNote`；`pricePending`填`billItemId,expectedRevision,priceId,reviewNote` |
| POST `/api/v2/patient-payments/receive` | 收费人员 `uc07.receive` | `receive`填`patientId,expectedFundsRevision,receivedCents,changeCents,channel,verification,receivedAt,transactionEvidence,externalReference,allocations,keepAsPrepayment`；`verify`另填`paymentId,expectedPaymentRevision,outcome` |
| POST `/api/v2/patient-payments/allocate` | 收费人员 `uc07.allocate` | `action:allocate/offset`、患者、原付款、资金及原款预期版本、`allocations` |
| GET `/api/v2/treatment-plans/query` | 牙医 `uc09.query` | `visitId,patientId`；返回该患者版本、项目、决定范围与本次执行链 |
| GET `/api/v2/services/options` | 牙医／收费／负责人 | 角色分别按执行、录入或确认价目权限读取目录及价目 |
| GET `/api/v2/patient-bills/query` | 收费人员 `uc06.query` | 必填`patientId`；可选`billId,from,to,pendingOnly,unpaidOnly,page,pageSize`；日期为上海营业日，结束日期包含当天 |

方案项目使用`description,toothCode,surfaceCode,quantity,estimatedCents`，估算可空，不产生应收。草稿`save`保留既有项目ID与顺序并允许末尾追加。改版`revise`需`expectedPlanRevision`及原版本`expectedRevision`；不传`items`时复制当前叶节点执行量以外的剩余数量，估算清空等待重新核对；传入`items`时形成牙医明确重新说明的新范围，项目均取得新ID。

决定`decide`需`decision,decidedAt,explanationBasis,scopeNote`，以及`itemIds`或`wholeScope:true`。整体范围由服务展开，不能用自由文本推算授权。代理及文书原件分别通过可选`proxyId,documentVersionIds`引用既有有效对象。直接决定不伪造签字文件；没有原件时仍需真实说明依据。

付款`verification`明确选择`confirmed`或`pending`；核实`outcome`选择`received`或`notReceived`。`allocations`每项为`billId,expectedRevision,amountCents,reason`。仅收预付或净到账额大于分配合计时，必须明确`keepAsPrepayment:true`，不能静默算作账目已付。无资金账户时`expectedFundsRevision:null`，已存在时从查询结果取得当前版本。

## 关键行为

- 方案提交说明后正文及项目冻结，实质变化建立新版本。改版时停止原已确认版本的后续执行；已被后续版本替代的旧待确认版本也不能重新获得执行权。历史内容、决定和原执行引用保留。
- 执行时按患者、版本、具体项目、真实决定时刻及同秒ID顺序核对同意；晚登记的同意不能倒填授权更早的执行。审计保存执行所据决定及具体范围ID。
- 计划完成量只合计更正链的叶节点；拒绝超量、跨就诊更正和更正分叉。同一阶段请求重试不会多写执行、应收或审计成功记录。
- 首次执行与应收依据共同提交；无适用价目时单价为空且状态为待核价，不能显示为零元结清。独立检查须由牙医明确选择并填写真实依据，不自动编造方案或判断治疗内容。
- 临床更正保留原应收，不自动生成第二笔收费；返回`EXECUTION_CORRECTED_FEE_REVIEW`，收费查询显示存在临床更正，差额后续经UC-24—26办理。
- 价目采用半开区间，发布时拒绝重叠；停止只影响新计费，不改历史单价快照。零价需明确免收依据。原待核价项目必须引用覆盖原发生时点的已确认价目，已核价后不能在原行重定价。
- 单项及汇总金额通过BigInt计算，再核对安全整数分范围，不使用浮点元金额累计。查询在同一读取快照内完成；费用结清与临床结束分开。
- 确认到账后原付款整行冻结；后续用途只追加分配或抵扣事实并递增资金、账目版本，不修改原款。到账核实与当次用途一起提交，任一用途失败会恢复原待核实状态。
- 付款分配和预付抵扣共用同一原款可用额，扣除成功退款及待办理/待核实退款占用；用途不能超过已核价未付。当前未接通退款写入口，但已用目标表中的真实状态夹具验证占用。
- 非现金交易号在写锁内按渠道查重，重复登记拒绝；原请求重试返回原阶段回执。净额、现金找零、实付时间及患者归属均重新校验；合并收款用途时还要检查分配权限。

## 尚未完成的边界

- 本批是后端，不代表32个用例或新增网页已全部实现。费用申请、批准和退费写入，以及复诊、材料、器械、采购等后续模块仍须逐步接入。患者付款是人工核实线下收款，不直接发起银行或支付平台扣款；组合付款按渠道分别登记原款。
- 代理、交接资格及文书原件引用读取现有表中的核实结果；对应维护、上传和物理文件校验服务尚未接入。不会生成假原件或默认承认自由文字代理范围。结构化代理范围当前使用`planVersionIds`与`operations:["decide"]`。
- 草稿项目删除受定稿DDL的事实禁止删除规则限制，当前按保留顺序逐项修改和追加处理；删减发布范围可在新版本中明确重列项目。新旧版本逐项语义对应仍由牙医核对，不按名称猜测临床关系。
- 已发布价目不能覆盖内容，历史引用的区间也不能强行截断。本批允许无重叠区间发布及停止旧价，不提供修改被引用旧区间来替换价目的快捷操作。
- 结束后的新增正常执行被拒绝；更正仅允许同就诊、保留同方案项目的链式更正。停用或结束范围下的首次历史补录尚未提供独立入口。
- 运行服务在3001端口，使用独立`clinic-v2.db`。旧版3000程序及其数据保持独立；旧数据未迁移。需求PDF和建表SQL摘要均与定稿基线一致。
