# 医保业务与字段对齐验收

依据现行164页需求文档UC-22、UC-23及其分析/设计模型。本轮修改运行代码与操作验收说明，需求PDF、LaTeX、77表986字段模型和原始SQL保持原摘要。

## 业务落实

| 文档要求 | 当前接口、存储及页面 |
| --- | --- |
| 身份核验 | 未通过且平台未返回时，人员编号及适用截止可空；通过仍须真实编号和有效期。未知不生成伪造结果。查询安全脱敏空值 |
| 逐项费用标识 | 每条原费用明确选适用医保编码或自费；不把缺编码自动变为自费。固定原提交、费用版本、数量金额和当时编码。编码标识不用于推算报销比例，实际分摊以核实的平台结果为准 |
| 原提交查询 | 可仅登记已经提交的预结算，分摊保持空；结果未知只能查同一原提交号。未知时不能重提、记录失效或转自费绕过 |
| 明确预结算结果 | 成功核对原患者、机构、原费用范围及分摊合计；失败、未知及成功分别追加历史，不记为收款。已明确的官方终端成功结果仍可一并录入提交和结果 |
| 失效与重提 | 原预估过期、身份或费用变化后保留原快照和选择，记录失效再重提；明确失败可按新号重提。新提交重置选择及预估。晚到成功遇到原费用/身份失效时，保存实际成功历史并共同标记失效，不复用过期结果 |
| 正式结算 | 采用确切当前提交、有效成功结果及本次患者医保选择。最终分摊按平台正式结果独立保存，不等同于医保到账或患者收款 |
| 撤销批准 | 负责人独立核实并批准原正式结算撤销，记录批准人、批准时刻和批准依据；可引用同账单已批准费用申请。待审申请不冒充批准，先独立批准原单撤销，再审核后续费用更正及患者退补，避免循环等待 |
| 撤销核实与重办 | 实际查询人及核实说明分列；未知/失败保留原正式效力，成功共同停用原结算和原办理。新办理显式引用同患者同就诊最近已结束原办理；不以新号绕过未决原单 |

## 数据库升级

- 版本`2026102304 → 2026102305`，精化5张医保表；新增9个设计字段，纠正7项可空定义，物理表数仍为108。
- `insurance_fee`按`(preestimate_request_id,bill_item_id)`唯一，重提保留原明细。原提交引用改为非空；金额、身份和编码快照受来源约束保护。
- 正式升级前自动生成一致性备份。本机原108张表的全部原列及行数摘要保持；外键错误0、完整性`ok`。本机旧医保表为空，未补造医保事实。
- 对有旧医保数据的库，只根据可验证的原提交、原字段及操作审计恢复新增关联。缺少确切原提交或最终核实人时，停止升级并保持原库；不会造一个历史请求或指定一个猜测的核实人。
- 隔离迁移测试涵盖有历史医保费用、正式结算、已撤销结果及旧待审申请的旧库，检查原事实与保留序号、可读备份、重复打开不再备份及中途错误整体回滚。

## 验收结果

- **373项自动化测试通过，0失败**，比上一批增加21项。
- **10个本轮医保网页场景、11个既有收付网页场景通过**，均使用隔离虚构数据，浏览器脚本错误0；检查390像素窄屏无页面横向溢出。
- 新增场景含明确自费、未返回身份字段、原预结算未知、失效重提、重新选择、晚到结果、费用实际更正、独立撤销批准、核实责任及原办理引用。
- 结构检查`npm run check:design`通过：77/77设计表名对应，模型指定的字段名、类型、可空、指定单列唯一、外键及主键无差异。
- 交付环境检查通过；3001本机服务已升级可用。正常库的医保资格仍未启用，支付及医保仍为人工核实官方终端结果，没有自动连接真实外部平台。

字段结构盘点不覆盖全部条件约束和业务语义，不能据此宣称整个D设计已经实现；下一阶段继续对照D2服务、实体和数据存取分层。本轮不改变精简后的业务范围。
