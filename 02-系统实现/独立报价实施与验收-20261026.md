# 独立报价实施与验收

依据180页需求文档UC-27“编制报价并记录患者确认”，落实独立报价及与原治疗方案、患者原款、实际费用的关联。2026-10-26，版本2026102602。

## 业务和办理顺序

1. 牙医登录后进入“独立报价”，核对患者与负责的来源就诊，选择已说明的治疗方案版本，或明确独立检查咨询。逐项选择收费项目、原方案项目，核对牙位牙面、数量、材料和疗程包含范围，保存草稿；未知金额保留空值。
2. 收费人员逐项明确选择已批准且出具时有效的价目，核对生效日期、患者接受截止日期和出具依据。出具冻结名称、单位、金额和范围；报价不会生成应收或营业收入。
3. 牙医或收费人员核对患者真实决定，明确勾选本次项目，登记接受、暂缓、拒绝或撤回以及实际时间和依据。决定只能追加。费用接受不替代治疗方案的医疗知情同意。
4. 需要变更时，由牙医建立新版本，收费人员重新核价出具。新草稿不使旧版立即失效；新版本出具时旧版才标记“已替代”。原患者决定、治疗、账目和收款保留。草稿可明确改接同一方案的新版本，已出具内容不能改指。
5. 收费人员可从报价页登记实际预付款，保留唯一原款记录和报价意向。实际到账、患者接受与实际账目分开核实，之后从“收费与退费”按原款抵扣实际应收。拒绝或撤回报价不会自动退款。
6. 牙医登记实际完成项目时核对对应报价。按原方案可自动核对唯一范围，独立检查可明确选择报价项目。实际数量或价目与已接受报价不符时保留真实治疗并形成待核价费用；负责人须核对重新说明并接受的报价范围与原实际发生时点价目，不能直接绕过费用决定。

接受截止日期包含当天。过期后不能新登记接受或倒填接受；已接受范围及其历史保留。报价、方案及费用的患者和来源版本必须一致；重复提交返回原结果，旧版本提交拒绝。

## 实现与数据

- `app/src/v2/quotes.js`组织编制、出具、逐项决定和岗位范围；`quote-repository.js`读取报价版本及历史；`quote-rules.js`核对费用决定、金额、预付款意向与实际执行。
- `quote-schema.js`以定稿报价补充DDL为输入，校验摘要后在一个事务中完成4表、2处引用、权限及冻结保护升级；数据库版本由2026102601升至2026102602。此迁移器负责升级，不能手动把设计补充SQL直接运行于实际库。
- 新表为`treatment_quote`、`quote_version`、`quote_item`、`quote_decision`；原表增加`patient_payment.quote_id`、`bill_item.quote_item_id`，与需求类表对应关系一致。原85表SQL未改。
- 实际3001服务已升级，原108表全部原行和原列核对保持，升级前备份可读。新报价表为空，未向实际库植入测试患者、报价、价目或费用。

患者统一工作区、日周日历、按岗位归集待办等新版表示层仍按后续分段对齐；其余D2分层也须独立核对。医保、支付真实平台联网和机构资质启用不属于本段已完成事项。本段未修改需求PDF及其范围。

## 报价演示

作业根目录双击`05-体验支付医保演示.cmd`，打开3002隔离业务演示；以`cashier`登录进入“独立报价”，可看到两项虚构后续治疗报价（400元及200元），逐项登记接受、暂缓或拒绝，再查看决定历史。以`dentist`登录可编制及改版。原600元医保演示费用与后续报价分开，报价不会增加原账单。演示时钟固定在2026-10-19，关闭后数据重置，不写3001业务库。

在app目录运行`npm run demo:quotes:v2`，或`../runtime/node.exe scripts/demo-v2-quotes.js`，可逐步复现两项出具、部分接受、100元原款预付及新草稿保留旧版事实。
