## 患者身份关联结构迁移

提供针对已识别的 112 表单店 SQLite 数据库的显式迁移脚本 `scripts/migrate-patient-identity.js`。该脚本要求绝对路径和现有数据库，迁移前创建备份，事务内添加身份关联表及防止改写和删除历史关联的约束，并拒绝连锁演示快照和未知版本。迁移完成的单店数据库可由现有数据库打开器识别；该步骤不配置可信身份服务、不启用真实身份登录，也不等于完成连锁正式数据库迁移。迁移前须停止访问目标数据库的服务并核对备份位置。

备份及连锁迁移预检同时识别原 112 表版本与包含身份关联的 113 表版本。预检在副本中核对表结构、外键、候选门店映射和相关记录，不自动填写无法核实的门店归属，也不会替代正式连锁迁移。

核对备份后，可用 `node scripts/prepare-chain-assignment.js <备份包目录> <模板 JSON 绝对路径>` 生成门店映射模板。模板列出需要归属的记录编号，所有门店字段留空，须由知悉历史业务的人员填写连锁、门店、岗位和每条记录的归属；不得把空值统一猜成某一家门店。模板绑定源备份数据库摘要，使用其他备份进行预检时会拒绝；模板不能写入备份包内，也不会覆盖现有文件。

`scripts/prepare-chain-candidate.js` 可在备份核对通过后，根据门店映射生成独立候选数据库：参数依次为备份包目录、门店映射 JSON、绝对输出路径；输出文件名必须为 `chain-migration-candidate.sqlite`，不能覆盖已有文件或写入备份包。映射除 `branchIds` 与 `tables` 外，还须提供 `chainName`、`branches`（每项包含 `id`、`code`、`name`）和 `staffRoles` 数组。岗位记录包含 `branchId`、`staffId`、`role`、`validFrom`、可选 `validUntil`、`grantedBy`、`grantedAt` 和 `evidence`；须核实人员已有相应岗位资格及授权人的本店负责人资格。空数组表示不迁移任何门店岗位，系统不会自行授予权限。候选文件用于核对数据和约束，当前系统尚未接入该数据库；实际门店归属和临床数据迁移需要由诊所核实。

候选生成时，备份中被数据库引用的影像与文书原件复制到同目录的 `chain-migration-candidate.files`，逐项核对大小和摘要；若文件目录已存在则拒绝覆盖。机构配置不会自动复制或启用。

生成后可运行 `node scripts/check-chain-candidate.js <候选数据库绝对路径>`，只读核对数据库完整性、门店归属字段、保护约束、原件及各启用门店的负责人、前台、牙医、收费岗位。输出中的 `blockers` 列出待解决事项；退出码 2 表示不能启用。检查不会确认历史门店归属是否真实，也不会更改数据库。正式连锁持久化运行入口尚未接入，因此即使其他检查通过，当前也不能启用该候选库。

`src/v2/chain-query-workspace.js` 为开发提供独立磁盘工作副本，已接入员工登录、按门店查询费用、跨店病历查询、授权登记与撤销、两店负责人协作授权及审计。它复制候选库及原件，不修改候选库；工作副本有独立标记，不能与候选库或正式业务库混用。该模块尚未完成正式连锁接线，不能用于诊所实际运营。

预约接诊、复诊和预约转店交接服务也已接到该工作副本。虚构数据已核对预约写入与资源占用、交接申请和拒绝跨重启保留；转店确认与复诊完整流程目前仍需进一步在磁盘副本中核对。现有内存演示入口继续使用受限的试验类。

病历草稿、开始接诊、诊疗记录和线下款项登记服务已接入该工作副本；目前已使用虚构患者核对病历草稿保存及线下收款登记重启后保留。其余诊疗动作及完整收费流程仍需继续核对；登记不触发真实支付。

治疗方案、独立报价、院外处方、文书、病历签署与补充服务亦已接入工作副本，院内发药在此副本默认关闭。当前虚构数据已核对方案编制和说明、报价草稿及重启后读取、文书原件下载和处方查询；处方开立、签署及其他变更还需继续在磁盘副本中核对。

可先用 `node scripts/prepare-chain-workspace.js <候选数据库绝对路径> <新工作副本绝对目录>` 创建开发副本，再使用 `node scripts/serve-chain-workspace.js <工作副本绝对目录> [端口]` 启动仅监听 `127.0.0.1` 的工作副本，默认访问 `http://127.0.0.1:3021/`。当前网页支持员工登录、切换岗位和门店、患者建档、发布门店排班、预约及取消、登记到诊、本人开始接诊和部分本店业务查询；它不提供真实患者登录或完整正式服务，不能用于实际诊疗。不要把该入口暴露到互联网。原演示网页仍使用独立的 3011 入口。

工作副本网页可保存本人本店的病历草稿、核对健康资料及签署病历；支持多药品院外处方草稿、开立、交付和核实后作废，多项目治疗方案、方案说明、报价草稿、收费人员核价出具，以及记录患者对整版或单个项目的方案和报价决定。牙医可依据已签署病历提出复诊要求并记录评估，责任前台可登记联系、关联预约或在符合条件时完成随访。收费人员可登记已核实的系统外收款；系统不调用支付渠道。填写的联系、评估、处方交付、到货和收款时间须与实际情况一致。

牙医可记录本人本店实际检查或已同意的方案项目，系统按该店可用价目形成费用明细，缺价则等待核价。结束实际操作后诊椅进入清洁准备限制，助理或负责人核实后恢复；故障维护类限制须负责人核实。

工作副本增加“费用更正与退费”页面：收费人员可依据本店已收费诊疗项目和原收款提交申请，负责人审核，收费人员核实系统外退款后登记。金额不能超过原项目和原付款用途的剩余额；此入口不发起真实退款。当前只覆盖与退费关联的单项诊疗费用更正，其他费用更正及预付款操作不在此页面提供。

工作副本可使用 `node scripts/backup-chain-workspace.js <工作副本绝对目录> <已有备份目录>` 备份数据库及对应影像原件，使用 `--verify <备份包绝对目录>` 校验，或使用 `--restore <备份包绝对目录> <不存在的新目录>` 恢复到新的隔离副本。备份和工作副本目录应相互分离；此工具不将工作副本转为正式数据库。云服务器衔接条件见上级目录的《云服务器衔接说明.md》。

门店采购页面支持单材料采购单、负责人确认、全部合格到货验收和批次核实放行，材料库存页面支持领用；负责人可按渠道核对并保存日终收退款净额。当前页面尚未覆盖采购多材料及拒收待检、材料退回等全部功能。日终结构只自动安装在经标识核对的开发工作副本，不会修改迁移候选库。

跨店页面已接入前台发起交接、目标店确认或拒绝、两店负责人协作授权、符合权限的撤销及牙医按授权范围查阅。已用不同门店虚构账号通过浏览器核对交接、授权、查阅与撤销后不可再查阅，并核对重启后数据。交接页面目前明确选择不额外预留设备，涉及其他设备的场景仍需进一步完善。

工作副本 API 还接入了本店库存、采购、价目、待核价和诊椅资源接口。虚构数据已核对二店价目拟定、提交及确认后持久保存，查询不混入一店价目，库存等业务的完整磁盘写入流程仍需继续核对。
