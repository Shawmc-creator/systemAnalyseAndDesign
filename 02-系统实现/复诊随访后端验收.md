# 复诊随访后端验收

日期：2026-10-19。依据定稿需求文档UC-12、UC-13、UC-14及诊后要求状态机实现，使用既有`followup_requirement`、`contact_history`、`clinical_assessment`三张业务表及统一审计、提交回执。85表基线、需求PDF及建表SQL均未修改，未执行旧数据迁移。

## 已实现

| 用例 | 岗位 | 本批实现 |
|---|---|---|
| UC-12提出诊后要求 | 牙医 | 引用本人负责或明确交接范围内的就诊/方案版本；指定目标、日期、是否评估及前台责任；待发布、发布、修改与有据撤销 |
| UC-13联系复诊与随访 | 前台 | 本人负责的已发布待办；逐次记录实际联系、未接通或拒绝；保留下一日期；责任转交；关联预约；需评估事项交牙医 |
| UC-14临床复诊与随访评估 | 牙医 | 记录实际到诊或远程评估；完成、继续跟进、另行处置；保留结论、下次日期和后续责任 |

来源病历签署、方案确认，以及预约取消或未到，会同步变更相关诊后要求。业务事实、关联变更审计及原命令回执在同一事务内提交；任一步失败共同回滚。

## 接口与输入

POST使用登录Cookie、当前`X-Clinic-Role`、`X-CSRF-Token`和`commandVersion:1,requestKey`。已有要求的修改及联系、评估须携带`patientId,followupId,expectedRevision`；当前版本从查询读取。每个独立动作使用新提交号，同一动作重试保留原提交号。

| 方法与路径 | 权限 | 操作与输入 |
|---|---|---|
| POST `/api/v2/followup-requirements/propose` | `uc12.propose` 牙医 | `create`：`patientId,sourceVisitId/sourcePlanVersionId,type,purpose,targetStart,targetEnd,requiresAssessment,responsibleFrontdeskId`；可填`nextContactDate` |
| 同上 | 同上 | `update`：要求当前版本、完整业务字段和`reason`；`publish`：核对来源及责任后发布；`cancel`：要求当前版本及`reason` |
| POST `/api/v2/followup-contacts/contact` | `uc13.contact` 前台 | `record`：`contactedAt,method,result,note,nextStep`；`transfer`：`responsibleFrontdeskId,reason` |
| POST `/api/v2/followup-assessments/assess` | `uc14.assess` 牙医 | `method,assessedAt,result,advice`；到诊检查另需`visitId`；完成需`assessmentCompleted:true`；继续跟进或另行处置需`nextDate,responsibleStaffId`，可指定`responsibleFrontdeskId` |
| GET `/api/v2/followup-requirements/query` | 牙医／前台 | 可选`patientId,status,from,to,overdueOnly,page,pageSize`；只返回当前授权范围，单页最多100条 |
| GET `/api/v2/followups/options` | 牙医／前台 | 返回当前具有有效前台或牙医资格及授权的工作人员，用于责任选择 |

`type`为“复诊/随访”。联系`result`为“已联系/未联系上/拒绝/待跟进”，`nextStep`为：

- `continue`：必须有`nextContactDate`。未联系上、拒绝、待跟进只能使用此动作。
- `arrange`：需`appointmentId,expectedAppointmentRevision`，引用经UC-01建立的有效同患者预约。
- `assess`：转为待到诊或评估，不能由前台作临床完成判断。
- `complete`：仅无需临床评估、无有效关联预约的待联系事项可用，需`goalAchieved:true,completionBasis`。

评估`method`为“到诊检查/远程沟通”；`advice`为“完成/继续跟进/另行处置”。日期使用`YYYY-MM-DD`，实际发生时刻使用带时区ISO格式。

## 状态与业务规则

1. 来源就诊须已结束且病历已签署，来源方案版本须已确认或本版执行完成且方案未终止。两类来源同时选择时均须就绪；否则先保存“待发布”，前台不可见。相同来源、类型和目的存在目标窗口重叠的未完成要求时提示已有事项。
2. 病历签署或方案决定形成后自动检查并发布待发布要求。指定前台已失效时保留待发布，避免阻断真实临床签署；牙医核对责任后可显式发布。来源后续发生变化时查询返回`sourceNeedsReview`，不自动改写原要求或原评估。
3. 已发布“待联系”事项须保留下次联系日期。继续办理时日期不能早于当前业务日期；逾期待办不自动消失。日期筛选按下次联系日期，无该日期时按目标开始日期计算。
4. 每次联系均追加不可改写的历史。未联系上或拒绝不等于临床目标完成；可以继续联系或由牙医有据撤销。转交不制造虚假的联系记录。
5. 预约须同患者、在目标日期内、发生于要求形成后，不能复用原就诊预约。随访接口只关联预约，不创建第二份资源占用；关联后再次联系沿用仍有效的预约。改约保持原预约关联，查询展示其当前时间和状态。
6. 取消预约或按实际截止时刻登记未到后，相关“待到诊或评估”要求恢复“待联系”，下次联系日期设为当日。保留原联系和预约事实，记录独立关联审计。牙医撤销要求不会替前台取消预约。
7. 到诊评估必须引用要求形成后的实际接诊；原来源就诊、尚未开始的登记以及时间不符的就诊不作为实际复诊。远程评估不关联虚构到诊。评估完成不自动结束另一次正在进行的就诊，也不改收付款。
8. 继续跟进或另行处置必须指定日期和有效前台/牙医责任人；牙医临床任务分配不会自动授予不相关病历访问权，联系责任仍由有效前台承担。
9. 当前状态机不提供待发布要求撤销或已关闭要求重开。已完成、已撤销事项冻结；新问题须另建有来源的新要求。来源标识不能通过修改要求改指其他就诊或版本。

## 权限与记录

- 前台只能办理本人负责的已发布要求，查询返回患者联系信息、实际联系及评估办理状态，不返回临床评估正文。
- 牙医须为来源或要求责任人、后续临床责任人，或在有效结构化交接范围内。交接`scope`以`followupIds/visitIds/planVersionIds`及`operations`明确限定；对应操作为`followup/followup.read/assess`。
- 负责人或收费人员身份不能直接替代牙医身份访问本接口。兼职人员须明确选择已获授权的当前岗位。
- 联系、评估按照实际发生先后追加；不接受未来时刻或倒序补录，本批尚无历史纠错入口。所有写入校验当前版本；同提交号重试返回原阶段回执，不重复追加。
- 联系或评估审计记录关联要求及前后版本；签署发布、预约取消恢复使用同提交号下独立的关联对象审计。
