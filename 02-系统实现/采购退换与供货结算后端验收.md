# 采购退换与供货结算后端验收

日期：2026-10-19。依据定稿需求文档UC-28、UC-29继续实现。沿用原85表SQLite结构，需求PDF、LaTeX及建表SQL未修改，未执行旧库迁移；新增网页与Figma仍按用户要求暂停。

## 本批范围

| 业务 | 岗位 | 已接入 |
|---|---|---|
| 采购差异 | 助理、负责人 | 助理按原采购/验收提出未交付取消、原拒收换货、已入库退供或换货、结算调整；负责人核对原版本批准或拒绝 |
| 实际退供 | 助理 | 按批准量分次交还供应商，引用原批次位置并扣减实际库存，保留原合格验收及入库事实 |
| 换货验收 | 助理 | 后续验收明确关联原批准差异，保留原拒收事实；已入库换货先实际退回原物；足额认可后结束差异 |
| 供货付款 | 负责人、收费人员 | 负责人核准具体用途及指定经办人，建立唯一办理号和占用；收费人员开始办理，再核实未知、失败、部分或全部实付 |
| 预付转结算 | 负责人、收费人员 | 负责人核准原款释放与目标用途，收费人员按授权执行；同一原付款形成成对用途事实 |
| 供货退回款 | 收费人员 | 引用同供应商原付款与已完成减款差异，记录实际收到的退回款及唯一渠道凭据 |

UC-28中单独的“补交”差异决议及完成跟踪尚未接入。现有未结束采购仍可按原确认约定继续分批验收；本批不宣称UC-28所有分支均已完成。

## 接口

POST沿用登录Cookie、明确的`X-Clinic-Role`、`X-CSRF-Token`及`commandVersion:1,requestKey`。每个独立动作使用新提交号，同一动作重试保留原号。数量为基本单位放大量，金额为整数分。现有对象须携带当前查询结果中的版本。

| 路径 | 权限 | 动作 |
|---|---|---|
| POST `/api/v2/purchase-receipts/receive` | `uc28.receive` 助理 | 原`receive/inspectPending`；新增`proposeIssue/returnGoods`；换货仍走`receive`并关联原差异 |
| POST `/api/v2/purchase-receipts/approve` | `uc28.approve` 负责人 | `approve/reject`差异决议 |
| POST `/api/v2/supplier-payments/authorize` | `uc29.authorize` 负责人 | `authorize`付款；`authorizeReallocation`原款用途转移授权 |
| POST `/api/v2/supplier-payments/pay` | `uc29.pay` 收费人员 | `initiate/verify/cancelUnstarted/reallocate/refund` |
| GET `/api/v2/supplier-payments/query` | 负责人／收费人员 | 必填`supplierId`；返回资金版本、原款及占用、分配与释放、退回款、采购及验收应付、差异和用途转移授权 |

原`GET /api/v2/purchases/query`增加采购差异集合。前台和助理身份不能读取供货资金接口；助理继续使用原采购、验收及库存查询，不返回患者病历正文。

### 差异与退换输入

`proposeIssue`：`purchaseItemId,expectedItemRevision,expectedPurchaseRevision,resolutionAction,quantityScaled,resolutionNote,reason`；引用验收时另需`receiptItemId,expectedReceiptItemRevision`。

- `cancelRemainder`：引用尚未交付量，不填写验收条目；有待检实物时先核清。已到货及已取消部分不能再次取消。
- `return`：引用原合格验收条目及拟实际退供量，金额按冻结采购价格与累计退供范围计算。
- `replace`：引用原条目；`issueKind`可明确“拒收/已入库退供”，混合条目默认按原拒收量提出。批准量不得超过对应来源剩余部分。
- `adjust`：引用原验收条目，`quantityScaled:0,adjustmentCents`为非零带符号分金额，不制造实物变动。

`approve/reject`：`issueId,expectedRevision,expectedFundsRevision,reviewNote`。批准后会检查本次提出依据中的采购、采购项目、验收条目版本；变化时须重新核对。拒绝不改变价款。

批准减少价款时，如原有效用途已超过调整后额度，另填`releases:[{allocationId,expectedRevision,amountCents,reason}]`共同释放原用途。释放限于同供应商的本采购或原验收、已确认原款的有效正向用途，且不超过本次价款减少；原记录保留，新增负向释放事实。未决付款占用不能通过此入口直接释放。

`returnGoods`：`issueId,expectedRevision,stockId,expectedStockRevision,quantityScaled,returnedAt,handoverEvidence`。实际交还须已发生且不早于负责人确认；原批次位置须有足够实物，累计不超批准量。可分次退供，足额交还后结束普通退货差异。受控退供可以处理隔离等不可普通领用的原库存。

换货使用原`receive`输入，每项增加`replacementIssueId,expectedReplacementRevision`。每次有独立随货依据。已入库换货先足额交还原物；认可及待检合计不能超批准范围。后续待检转认可继续使用原`inspectPending`；足额合格才结束原差异，失败或待检事实保留。

### 供货付款输入

`authorize`：`supplierId,expectedSupplierRevision,expectedFundsRevision,requestedCents,channel,cashierId,reviewNote,allocations`。

用途每项为`{kind:'order'/'receipt',id,expectedRevision,amountCents}`。用途须同供应商，合计等于本次拟付。采购预付与验收结算共用原采购总额度，同时单独检查验收认可应付。每个供应商有未决付款时，先核实原办理号。

授权建立“待付款”和等额“待生效”用途；`operator_id`为负责人指定的收费经办人，实际授权人及操作人分别留审计。授权依据固定当时的供应商版本、结算依据和目标版本，此时实际支出仍为零。

`initiate`：`supplierId,expectedFundsRevision,paymentId,expectedRevision,transactionEvidence`。仅指定的当前有效收费人员可接收办理；开始前再次检查供应商和目标版本。已开始的办理不能另起一次线下付款。

`verify`：上述原款与版本字段，加`outcome:'success'/'failed'/'unknown',transactionEvidence`；有实际观察金额时填`actualCents`。成功另需`recipientMatches:true`及非现金的`externalReference`。

- 全部实付可沿用原核准用途；部分实付须给出`actualAllocations:[{allocationId,amountCents}]`，每项不超原范围，合计等于实付。
- 未知保留全部原占用。报告失败却有正金额、金额超拟付、接收方不符或非现金缺交易号，保存“待核实”并返回`SUPPLY_REVIEW_REQUIRED`，观察值进入审计。
- 核实失败且实际金额为0，取消待生效用途。重办由负责人重新授权，并以`previousAttemptId`关联同供应商明确失败、尚未重办的原办理；不能分叉重办。
- `cancelUnstarted`只取消尚未开始线下办理的授权，保留失败/未办理依据并释放占用。已经开始须核实原结果。

### 预付转结算与供货退回款

`authorizeReallocation`：供应商及原款版本字段、`reviewNote,releases,allocations`。负责人授权记录保存在既有操作审计的结构化授权快照中；返回的供应商资金版本随之递增。收费人员从查询的`authorizations`读取授权`id`。

`reallocate`：`supplierId,expectedFundsRevision,authorizationId`。执行时检查原资金版本、供应商版本、原款、原用途及目标版本。先新增负向释放，再新增原付款的正向有效用途，整体提交；不会新增付款。资金或原单变化后，旧授权须重新核实。同提交号重试返回原回执。

`refund`：`supplierId,expectedFundsRevision,paymentId,expectedRevision,issueId,expectedIssueRevision,receivedCents,channel,receivedAt,senderMatches:true,transactionEvidence`，非现金另需`externalReference`。

退回款须已实际收到，引用同供应商已确认原款及已完成的负向减款差异；原款须有对应采购或验收的历史用途。累计不超该差异减款剩余额及原款已释放可用额。换货额度不能直接登记为退款；实物退货尚未完成时也不能登记为已完成退货的退回款。

## 表与一致性

- 沿用`purchase_issue`、`supplier_funds`、`supplier_payment`、`supplier_allocation`、`supplier_refund`及既有库存表。`purchase_issue.resolution`保持原“换货、退货、取消剩余、价款调整”等枚举；`reason`使用带版本的结构化依据，保留实际原因、处理说明、原单版本和后续换货条目索引。查询资金差异时提供解析后的`basis`。
- 已确认采购约定和原合格/拒收事实保留；退供另有流水，价款另有差异。换货的采购总额度保持原约定，原退供验收减少的价款与后续换货验收对应，避免再计一次采购。
- 已履行完成的采购项目按原状态机保留终态，后续退换由独立差异记录展示。未交付取消量及退换数量分别计算，不用覆盖原约定量抹平差额。
- 拟付与等额占用、首次实际确认与等额有效用途、失败与占用取消分别同事务提交。已有原款的有效用途、释放和实际退回款共同受余额限额。
- 银行/微信等外部交易号在写锁内查重；同一办理已关联的交易号不能更换。成功付款、失败原办理、已生效用途、实际退回款及结束差异保持冻结。
- 同一提交号返回当时阶段回执；当前进度从查询读取。业务事实、关联换货差异、资金版本、提交回执及审计共同成功或回滚。
